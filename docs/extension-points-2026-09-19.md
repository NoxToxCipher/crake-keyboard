# What the platform still has for Crake

_Researched 2026-09-19 by four agents against the live Android docs and this repo; every claim below was re-checked against the source before it was written down._

**Two things before the list.**

First: someone is in this tree right now. `git status` in `C:/Users/lochr/crake-keyboard` shows uncommitted edits to `app/src/main/kotlin/dev/patrickgold/florisboard/ime/editor/EditorInstance.kt`, `libnative/crates/crake-core/src/nlp.rs` and `core_dict.rs`, plus an untracked `libnative/crates/crake-core/tests/given_names.rs`. Both halves of the field report are already half-answered in that working copy. Don't re-do them; read them first.

Second: the brief I was handed says "no telemetry that leaves the device." The code agrees — but `app/src/main/AndroidManifest.xml:11` says INTERNET is there for the "OTA Auto-Updater and Flight Recorder Diagnostic Uplink", and `app/src/main/kotlin/dev/patrickgold/florisboard/ime/nlp/DiagnosticSyncManager.kt` exists. I read it: there is no network code in it at all (`FileWriter`, no `HttpURLConnection`, no URL), and it hard-stops at `2026-09-06`. So the position holds in fact, but the manifest comment and 324 lines of dead sprint plumbing are the first thing a sceptical reader will find. Delete or rename them before anyone audits you.

## Do these first

**1. Make the keyboard usable with TalkBack.** Nothing in `app/`, `lib/`, `ROADMAP.md` or `README.md` mentions accessibility — zero hits for `ExploreByTouchHelper`, `AccessibilityNodeInfo`, `announceForAccessibility`, `isTouchExplorationEnabled`, `clearAndSetSemantics`. The only `semantics {}` in the whole repo is `lib/snygg/.../SnyggButton.kt:77`; the only `contentDescription` values in `TextKeyboardLayout.kt` are at lines 8419/8435/8463 on easter-egg artwork. A blind person installing Crake today gets silence over a grid of rectangles.

The researchers said you'd need a virtual view hierarchy. You don't, and this is the good news. Each key already *is* a composable — `TextKeyButton` at `TextKeyboardLayout.kt:7932`, emitted per key in the loop at line 981 — so every key has real layout bounds. `Modifier.semantics` with `contentDescription`, `Role.Button` and an `onClick` action is the right tool, not `androidx.customview.widget.ExploreByTouchHelper`.

The real obstacle is one line the researchers missed: the parent `pointerInteropFilter` at `TextKeyboardLayout.kt:428` swallows every `MotionEvent` and hands it to `controller.onTouchEventInternal` (line 8819), which does its own hit testing and drives the swipe and glide detectors. Under touch exploration that pipeline never sees a raw event, so semantics nodes need an activation path that doesn't go through it. Glide and swipe gestures will simply be unavailable with TalkBack on, and that's fine — say so in the settings copy.

Cost: a week, honestly, not a day. Gate the lift-to-type mode on `AccessibilityManager.isTouchExplorationEnabled()` (API 14). **First step:** add `contentDescription` to `TextKeyButton` from `evaluator.computeLabel()`, install TalkBack on the emulator, and see how far explore-by-touch gets before the pointer filter eats it. That one hour tells you the shape of the rest.

Two things to fold in. `AccessibilityManager.isHighContrastTextEnabled()` and `addHighContrastTextStateChangeListener(Executor, listener)` are API 36 — I confirmed both in the SDK's own `platforms/android-36/data/api-versions.xml`, and you already compile and target 36. And there is a platform attribute nobody mentioned: `android:supportsInlineSuggestionsWithTouchExploration`. Its documentation in `platforms/android-36/data/res/values/attrs.xml:4166` says inline suggestions are off under touch exploration unless an IME opts in, and that "most IMEs should not set this to true" because menu-style Autofill works better. Crake declares `supportsInlineSuggestions="true"` in `res/xml/method.xml` and not this one. That's the correct state — but now you know it's a deliberate choice rather than an oversight.

**2. Finish the fada.** The in-flight `GIVEN_NAME_CASING` table in `nlp.rs` is 80-odd names and contains **zero accented characters** — I grepped the diff for `é á í ó ú` and got 0. It has `roisin`, `sinead`, `ruairi`, `aine`, `gearoid`, `blathnaid`, `padraig`, `mairead`. So Aoife works now and Róisín still doesn't, which is the same complaint one layer down. There's no Irish layout either: `ls app/src/main/assets/ime/keyboard/org.florisboard.layouts/layouts/characters/` has esperanto, icelandic, igbo, rusyn, udmurt — no irish or gaelic — and `LANGUAGEPACKS.md` never says Irish. Cost: hours. **First step:** add the accented spellings as dictionary entries in their own right and make the ASCII form suggest the accented one, the same way lowercase suggests capitalised.

**3. Mark what Crake copies as sensitive.** `ClipDescription.EXTRA_IS_SENSITIVE` is API 33. Crake reads it off incoming clips (`ClipboardDatabase.kt:135`) and attaches it to nothing it writes — I checked all eight `setPrimaryClip` call sites. The one that matters is `app/settings/crypto/CrakeEncryptionScreen.kt:68`: copy decrypted text out of Crake on Android 13+ and the system flashes the plaintext in a preview toast. Half a day. **First step:** a helper in `lib/android/.../AndroidClipboardManager.kt` that takes a sensitivity flag, then fix the crypto screen, then the vault and snippets paths.

**4. Stop paying for cursor geometry you throw away.** `AbstractEditorInstance.kt:113` calls `requestCursorUpdates(CURSOR_UPDATE_MONITOR or CURSOR_UPDATE_IMMEDIATE)`, and `onUpdateCursorAnchorInfo` is overridden nowhere — zero hits for `CursorAnchorInfo` in `app/` or `lib/`. The researchers described this as asking "every frame"; it's requested once per editor session, and `MONITOR` then makes the *editor* push a `CursorAnchorInfo` across the binder on every cursor move and layout pass for the whole session, into `InputMethodService`'s no-op. Same waste, different mechanism. The two-argument `requestCursorUpdates(int, int)` and the `CURSOR_UPDATE_FILTER_*` constants are API 33 (verified in `api-versions.xml`). Until you consume the data, drop `MONITOR`. Two lines.

## Worth doing eventually

`InputConnection.getSurroundingText` (API 31, returns `SurroundingText`) replaces **three** round trips, not two — `AbstractEditorInstance.kt:131-133` calls `getTextBeforeCursor`, `getTextAfterCursor` *and* `getSelectedText`, and `SurroundingText` carries the selection offsets. But note the motivation the researchers gave is gone: the double-space fix landed in `EditorInstance.kt:222` as `if (activeContent.textAfterSelection.startsWith(' ')) return false`, using data the editor already had. This is now a tidiness-and-IPC item, not a bug fix.

`SuggestionSpan` (API 14; `FLAG_MISSPELLED` and `FLAG_EASY_CORRECT` since 14, `FLAG_AUTO_CORRECTION` since **15**, not 14) is the honest answer to "the mistake never corrects": a dotted underline at the word in the target app, which matters because `method.xml` sets `suppressesSpellChecker="true"`, so while Crake is up the system draws nothing. One caveat the researchers didn't give: the suggestion popup lives in `android.widget.Editor`, so expect it in classic `EditText` and expect Compose `BasicTextField` and WebView editors to drop it silently. Spike it across four apps before committing.

The small pile, all verified as absent and all a few lines each: `onCustomImeSwitcherButtonRequestedVisible` (API 36 — and you target 36, so Android 16 behaviour already applies in the field), `setPhysicalKeyboardHint(ULocale, String)` and its sibling `setSubtypeNameOverride(CharSequence)` (both API 34), `setImeConsumesInput` and `performSpellCheck` (both API 31).

The bigger pair is one project, not two: a `.combined` wordlist importer plus a data-only `.flex` extension type. `ExtensionManager.kt` registers exactly three subclasses today, and `app/src/main/assets/ime/dict/` holds one English blob. Helium314's aosp-dictionaries does list Irish under CC BY 4.0, last updated 2026-05-24 — but it is **841,939 entries**, against your 652KB `data.crkd`. That size is the argument for import rather than bundle, on top of the licence one: GaelSpell is GPLv2 and about 390,000 words, so it can never ship inside an Apache-2.0 APK, but a user importing their own file is fine. If you want hunspell morphology, `zspell` is pure Rust with no C backend and a stable checker; its suggestion API is explicitly not finalised, so use it for validity, not ranking.

Stylus is real but the recogniser is the whole cost. The plumbing is confirmed: `android:supportsStylusHandwriting` exists in the SDK's `attrs.xml:4211`, `onStartStylusHandwriting` and friends are API 33, `onUpdateEditorToolType` is 34, connectionless is 35, `setStylusHandwritingRegion` is 36. Gesture classes (`DeleteGesture`, `SelectGesture`, `InsertGesture`, `RemoveSpaceGesture`, `JoinOrSplitGesture`) and `performHandwritingGesture` are all API 34. The researchers' best idea in the whole batch is buried in a note: **gestures without transcription**. Scribble-to-delete and circle-to-select are geometry, and `crake-core` already has `hit_test.rs` and `glide.rs`. No model, no download, no licence. Check `EditorInfo.getSupportedHandwritingGestures()` (API 34) before offering one.

## Refuse

`TextClassifier` is worse than the researchers said. On Android 11+ `getTextClassifier()` returns the ExtServices implementation — `com.android.ext.services`, a separate updatable Mainline module — and `getLocalTextClassifier()` was reduced to a NO_OP in the same release. There is no in-process option anywhere in Crake's supported range. Every call ships the user's text to a Google-signed process you cannot read. Build URL/email/phone detection in `crake-core` instead.

ML Kit Digital Ink downloads about 20MB per language through `RemoteModelManager`. ML Kit Smart Reply, Entity Extraction and anything via AICore or Gemini Nano: a keyboard that suggests replies has read the conversation, and the model is unauditable. Plain `SpeechRecognizer.createSpeechRecognizer` routes audio to Google's servers and `EXTRA_PREFER_OFFLINE` is a hint. `triggerModelDownload` (API 33) is a network fetch and must never fire on its own. Cloud clipboard and downloadable-font EmojiCompat both put traffic on the wire for no product gain.

`READ_CONTACTS` for Irish names: don't. It's the largest privacy ask on the list and you have a better answer already running — a curated names table, which also helps Welsh, Icelandic and Polish typists, and which needs no permission and no dialog.

On-device speech (`createOnDeviceSpeechRecognizer`, API 31) is the only genuinely hard call. It keeps audio off the network but hands it to Android System Intelligence, a Google app you can't audit — better than today's `switchToVoiceInputMethod` (`FlorisImeService.kt:255`, which hardcodes the string `"voice"` because `SUBTYPE_MODE_VOICE` is private), and worse than in-process. My read: leave it. A keyboard whose pitch is "nothing leaves the process" should not ship a microphone button whose honest label is "this goes to Google, just not over the internet." Park it behind whisper.cpp in `libnative`, or not at all.

## Where the researchers were wrong

The double-space bug was described as unfixed and as needing `getSurroundingText`; it is fixed in the working tree and needed neither. The key grid was called "drawn, not composed" — it is composed, per key, which makes the accessibility work cheaper and points at a different tool. `requestCursorUpdates` was described as a per-frame request; it's a once-per-session request with per-frame consequences. `getSurroundingText` was credited with halving two IPC calls; it replaces three. `EXTRA_IS_REMOTE_DEVICE` was listed as API 33 — it's 34, and amusingly the repo already gets this right at `ClipboardDatabase.kt:141` while the researcher's own description of that code says otherwise. `FLAG_AUTO_CORRECTION` is API 15. And nobody looked at `supportsInlineSuggestionsWithTouchExploration`, which is the one platform attribute that connects the accessibility item to something Crake already declares.

Everything else in their API-level claims I checked against `C:/Users/lochr/android-tools/sdk/platforms/android-36/data/api-versions.xml` — Google's own shipped metadata — and it held.
